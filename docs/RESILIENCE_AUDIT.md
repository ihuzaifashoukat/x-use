### Session and account lifecycle

The async runtime launches one Chromium process and creates an isolated in-memory context for each active account. Each context has its own cookies and proxy route. There is no shared persistent profile directory, cookie snapshot rotation, automatic identity rotation or cross-account storage reuse. A warm context is reused while healthy, preserving an unlocked inbox until explicit closure, idle expiry or server shutdown.

Before context creation, cookie validation checks exact X domains, authentication-cookie uniqueness, secure flags and expiry. An OS-held lock based on the authentication identity prevents two local processes from driving the same imported account. Individual operations are serialized. Capacity is bounded and idle contexts are closed; shutdown awaits tracked cleanup tasks. Context separation follows the [browser-context isolation model](https://playwright.dev/python/docs/browser-contexts), while all contexts still share one browser process and host.

This design avoids persistent-profile corruption and unnecessary chat reloads, but it deliberately does not save refreshed cookies, encryption keys or decrypted chat state. Restarting reuses the operator's original cookie export, which can eventually expire. Recovery requires fresh authorized credentials or an explicit owner unlock when the current UI demands it. The runtime does not fabricate a renewed login.

Actions use native visible-page interactions with exact target and recipient verification. There is no claim that random delays, mouse movement or a patched browser make an authenticated account anonymous. Durable caps, spacing, challenge stops and uncertainty tracking limit activity and duplicate attempts; they are local operating controls, not platform-approved usage allowances. Patchright's documented patches apply to Chromium and do not establish account-level undetectability ([driver documentation](https://github.com/Kaliiiiiiiiii-Vinyzu/patchright)).

### Residual boundaries

State files are not encrypted. SQLite state on Windows now requires a verified owner-private parent directory before opening a connection. Newly created state directories have private inheritable ACLs; WAL, shared-memory and rollback-journal files inherit them. Existing broad directory ACLs or permissive sidecars fail before SQLite writes and require operator remediation. Tests inspect real sidecar ACLs and prove that rejected existing paths remain unchanged. Previously open handles, local administrators and malicious code running as the same user remain outside this protection. The server rejects linked state paths and does not rewrite permissions on existing directories.

The earlier extension relied on driver/context completion and retained ownership on reported cleanup failures. The follow-up review added owned-process enforcement after reproducing surviving browser processes, as described above. Locks still coordinate one host and do not provide a distributed account lease. Proxy routing does not protect against a compromised host, proxy or browser, and authenticated account activity is visible to X.

Native fixtures cover multi-part posts/replies, media upload, parent chaining, uncertain outcomes, cancellation, stale confirmation and restart behavior. A live context read returned four distinct posts, including the exact focal post, and two mapped image blocks; it reported `partial=true` with `stop_reason=no_growth`.

## Original baseline: result and support boundary

The MCP server defaults to async Patchright with optional Playwright compatibility. It exposes 64 tools and six workflow prompts, including 31 browser, inbox, recovery and outreach tools. A shared policy boundary applies durable budgets and records uncertain outcomes for approved drafts, immediate actions and queue execution. Messages and follows always need individual draft approval. Campaign preparation creates local drafts; it never sends a batch.

This is a browser application with changing upstream pages. It cannot guarantee freedom from account restrictions, perpetual selector compatibility, or successful operation on every device. Supported development targets are desktop Windows, macOS and Linux with Python 3.10 or newer and a compatible Chromium browser. Mobile operating systems are not native server targets; a mobile MCP client needs a separate host running the server.

The default backend deliberately stops for login challenges, rate limits, unidentified recipients, unsupported pages and unconfirmed outcomes. The legacy Selenium CLI and batch pipeline dependencies remain available for explicit compatibility use. Community audience verification and the legacy `run_cycle` batch path have not been migrated to the async browser runtime.

| Stale post confirmation | A previous success toast could falsely confirm a new submission. | Capture existing toast permalink IDs before the click and exclude them from new outcome evidence. | Native fixtures on both drivers reject the old permalink and accept a newly observed one. |
| Opt-out bypass | Updating a lead or creating another campaign could reopen a suppressed recipient. | Account-scoped permanent handle suppression, rechecked at approval and immediately before sending. | Outreach and MCP integration tests cover alternate campaign/direct-send paths. |
| Recovery race | Reconciliation could mark an action `not_sent` while it was still running. | A separate OS operation lock spans browser work and reconciliation for one account/database. | Integration test attempts reconciliation during an active send and receives `account_busy`. |
| Cross-store crashes | SQLite campaign state and JSONL drafts cannot commit as a single transaction. | Pending reservations remain reserved after interrupted preparation. Confirmed-delivery bookkeeping can be repaired by action ID without another send. | Crash and idempotent reconciliation tests. Missing draft records require operator inspection. |
| Draft recovery | A preflight rejection could strand an otherwise usable draft. | Preserve pending drafts when no browser attempt was reserved. Attempts with unknown outcomes become uncertain. | Paused-campaign recovery test and timeout tests. |
| Client cancellation | MCP client cancellation could leave a draft in the transient approved state. | Handle cancellation explicitly, retaining pending status without a reservation or uncertain status with a recoverable action ID. | Cancellation tests hold reservation and send operations at deterministic boundaries. |
| Inbox completeness | Virtualized or encrypted interfaces can conceal older conversations/messages. | Reads explicitly return `partial=true` and `pagination=visible_only`; unsupported views cannot masquerade as empty inboxes. | Empty/unknown-UI fixtures. Full historical export, attachments and guaranteed unread state are not provided. |
| Inbox navigation | Repeated hard navigation discarded the active chat component and caused unnecessary reloads after unlock. | Enter `/i/chat` directly, reuse the ready chat view, select an exact visible conversation row through its native SPA interaction, and wait for history evidence. | Navigation-count regressions distinguish initial entry from subsequent inbox/search/history reads. Live confirmation is recorded in the runtime guide. |
| PIN handling | A PIN exposed in a tool argument or driver exception could enter logs or stored state. | PIN comes from a restricted server environment variable and is used once; DOM exceptions are sanitized. | Tests inspect results and persisted policy data. PIN entry requires a recognized owner unlock screen; there is no guessing or automatic retry. |
| State privacy | Lead notes, drafts and delivery state are sensitive local data. | Runtime paths are ignored by Git; managed state files have explicit permissions. No browser cookie snapshots or decrypted chat state are persisted. | The current extension above supersedes the original inherited Windows permissions with verified file ACLs. Local administrators and the server operator retain access. |
| MCP transport | Import-time diagnostics could corrupt stdout before the protocol started. | Lazy MCP package loading and early stdout redirection for both module and CLI entry points, preserving the SDK's binary transport. | Clean-wheel smoke validates initialization, the tool inventory and protocol stream purity. |

## Runtime operation and state

The tool layer validates arguments and resolves the configured account. Local tools inspect account metadata, drafts, lead records and policy state without starting a browser. Browser reads reserve a bounded attempt and then acquire an account context. Writes reserve a durable action before startup, recheck policy at the commit point, operate on a verified UI target and record observed evidence.

The safety ledger stores action metadata, hashes, timestamps, outcomes and recovery references. It does not store message bodies, cookies or PINs. The outreach database does store the lead information supplied by the operator. The draft JSONL stores exact reviewable text. These files should live in a private local directory; ignoring a file in Git does not encrypt it.

Contexts do not persist profiles. Restarting the server authenticates from the original cookie export again. Closing a context discards its in-memory browser storage. Separate contexts provide session isolation; they are not a security sandbox against a malicious local operator or compromised server process.

Defaults are conservative local budgets: 300 reads, 5 posts, 15 replies, 30 likes, 10 retweets, 10 messages, 10 follows and 5 unlock attempts per UTC day. Read spacing is two seconds, write spacing ninety seconds, and the shared minute budget is six attempts. Failed attempts count. These numbers are configurable policy choices, not platform-published allowances.

An error provides a stable `reason` and, when relevant, `retry_after_seconds` or `action_id`. A caller must not interpret a timeout as proof that nothing happened. Inspect the account and action ledger before calling `resolve_action_outcome`. Reconciliation does not reset daily budgets or bypass a challenge.

## Inbox test scenarios

The test suite separates the DOM adapter from MCP approval and persistent delivery accounting. Synthetic browser pages use intercepted local responses with no X credentials. The following scenario groups are covered or explicitly limited:

- Read recognized inboxes, recognized empty states and bounded visible conversation histories; reject unknown/ambiguous layouts rather than return fabricated empty results.
- Validate numeric and opaque chat references, allowed hosts, path boundaries, malformed URLs and hostile navigation input.
- Match exact recipients, reject prefix matches, distinguish conversations from compose routes and recheck the route/header before sending.
- Handle rendered message direction, IDs, multiline/Unicode text, duplicate prior text and pending outgoing states without counting an old message as delivery evidence.
- Stop for expired login, challenge, locked account, rate limit, PIN requirement, missing/ambiguous composer and disabled send controls.
- Check explicit unread evidence and report an unknown state when the page supplies no reliable indicator. Opening a chat may generate a read receipt in X.
- Exercise one-shot PIN unlock, invalid PIN UI, unsupported layouts, disabled confirmation and asynchronous readiness without persisting the PIN.
- Verify individual draft approval, rejected preflight recovery, opt-outs after preparation, paused campaigns, interrupted writes and bookkeeping recovery without resending.

Live verification uses `scripts/inspect_x_session.py`. Its output is limited to counts, recognized selectors and status metadata. It never exports cookies, PINs, message bodies or full DOM snapshots. Live results and unsupported cases are recorded in [BROWSER_RUNTIME.md](BROWSER_RUNTIME.md). Offline fixtures establish adapter behavior; they do not establish compatibility with every current encrypted inbox rollout.

Authorized operator tests additionally delivered one personalized DM and one public reply through individually reviewed registered MCP drafts. DM confirmation required a newly observed local pending-to-sent UUID row and a cleared composer. A fresh MCP read of the public reply permalink matched its exact submitted text. Public profile feeds and following rows were also read. Initial native UI mismatches stopped before submission, were inspected and explicitly reconciled, and supplied concrete regression cases. No write after a native submission was retried. Final local account inspection reported no unresolved uncertain actions. Private operator reports remain ignored and are not CI artifacts.

## Operator verification and release gates

The final local regression run on Windows with Python 3.14.7 passed 1,468 tests in 531.34 seconds. Three POSIX file-permission cases were skipped on Windows. Two existing UTC timestamp deprecation warnings came from the legacy metrics module. The suite included intercepted Chromium fixtures for both async drivers, including chat reuse, delayed recipient identity, UUID-bound message bodies and reply composer targeting. These results establish local behavior; they do not establish remote OS matrix or container success.

The final wheel and source distribution passed strict metadata checks. The wheel was reinstalled into a clean environment outside the checkout, without optional Playwright or editable source imports. All 98 source modules and five bundled skills matched the wheel, source archive and installed package byte for byte. Dependency consistency, both MCP entry points and the bundled Patchright Chromium smoke passed. Both entry points exposed 64 tools and six prompts with zero malformed protocol messages; the intercepted browser smoke forwarded no external requests. All five required native browser modules passed against the installed wheel: 171 tests, zero skips and zero failures in 195.68 seconds, using bundled Patchright Chromium.

From a checkout, run the one-command setup described in the README. Run `x-use doctor`, configure an authorized account with a private cookie file, and inspect `get_session_status` and `get_account_safety` before browser work. Stage a draft, inspect its full payload, and approve only the intended individual action. Keep autonomous queue draining disabled unless deliberately configured.

For release verification, the workflow resolves dependencies, runs the offline regression suite, checks Git ignore invariants, builds both distribution formats, validates package metadata, and tests the installed wheel. Browser smoke pages are synthetic and contain no personal accounts. Diagnostic artifacts may contain only synthetic screenshots/traces. No live cookies, PINs, inbox state or account configuration are uploaded to CI.

All workflow actions are pinned to verified commit IDs. CI has read-only repository permissions; release jobs receive OIDC permission only where publishing requires it. The registry publisher is version-pinned and its reviewed release-asset SHA256 is checked before extraction. Docker build contexts allow only package metadata and source, excluding private account files and development artifacts. The browser image runs under a non-root account and installs browser binaries matching its Patchright package. The small default image supports package/MCP introspection; choose the browser target for actual browser operation.

The dependency lock makes the uv setup reproducible, while the pip matrix also checks resolution of currently compatible dependencies. Separate advisory jobs use an isolated, pinned pip-audit against a hashed lock export, fail on published findings, and retain JSON diagnostics. The local Windows Python 3.14 scan checked 92 packages with zero known findings and zero skipped packages; a deliberately vulnerable test requirement correctly failed the scanner. This covers known Python package advisories, not browser binaries or application code. Review and regenerate the lock intentionally when upgrading packages. Neither a lockfile nor passing tests proves there are no vulnerabilities; a future dependency or upstream UI change needs another review.

## Follow-up boundaries

Additional encrypted chat layouts need live, authenticated UI evidence before new selectors can be accepted. Full-history pagination, inbox attachment delivery and community audience verification remain outside the implemented surface. Post and reply attachments are supported by the current thread extension. Moving the remaining legacy batch engine off Selenium is a separate compatibility migration. Unsupported cases return explicit results.
